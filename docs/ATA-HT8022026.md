# The analog adaptor — Telno HT8022026

What the box actually is, measured on a live unit (`192.168.1.45`, firmware 1.0.x,
`mini_httpd 1.30 26Oct2018`), and why the console talks to it the way it does.

This is written down because the device is unusual in ways that look like faults:
the first four things a normal HTTP client does all fail against it, and none of
those failures are the device being down.

## What it is

| Fact | Measured value |
|---|---|
| Web server | `mini_httpd/1.30 26Oct2018`, `Server: Grandstream/1.10` on CGI pages |
| Login page | static `/index.html`, 2094 bytes, jQuery 1.x, "All Rights Reserved … 2006-2020" |
| Console | server-rendered CGI at `/cgi-bin/<page>`; no JSON API for state |
| Open ports | 80 only. No 443, no 8080; SIP/5060 was closed on the audited unit |
| Process report | `/cgi-bin/api-get_system_status` → `{"vsz":"16480","command":"ata"}` |

The unit is an **HT802 (V1-era firmware)**, not the HT802 *V2*. That matters: the
V2 is a Vue single-page app with a documented JSON API (`/cgi-bin/api.values.get`,
P-parameter reads). This firmware has no such endpoint — eight plausible
`api-get_*` paths were probed and only three answer. Anything written against the
V2 API silently does nothing here.

## The four things that fail, and why

### 1. Two status lines in one response

```
HTTP/1.0 200 OK\r\n
HTTP/1.1 200 OK\n
Content-Type: text/html; charset=utf-8\n
Server: Grandstream/1.10\n
\n
\n
<html>…
```

mini_httpd writes the wrapper status and the CGI writes its own. curl stops at the
second with `Header without colon` and returns an **empty body**; `fetch`/undici
rejects the whole response. A correct password therefore looks exactly like a
device that returned nothing.

### 2. The CGI's shebang is emitted as a header

```
HTTP/1.0 200 OK\r\n
#!/bin/ash
Cache-Control: no-cache, must-revalidate\r\n
Content-Type: application/json\r\n
```

Any strict parser treats `#!/bin/ash` as a malformed header line.

### 3. Headers are LF-only, mixed with CRLF

The same response uses `\r\n` on the first line and `\n` on the rest, so splitting
on `\r\n\r\n` alone finds no header terminator at all.

### 4. "Sign in" is a bodyless 301 with no `Location`

Every path under `/cgi-bin/` answers a session-less request with `301` and a
`Moved Permanently.` body, with **no `Location` header**. Which means:

- there is no way to tell "this page exists" from "this page needs a login";
  a 54-name probe of plausible page ids returned 301 for all of them, so page
  discovery by probing is impossible (that oracle is dead — do not rebuild it);
- it is not a redirect a client can follow.

## How the login works

The login page's own `checkForm()` does the encoding:

```js
input_pwd.value = btoa(input_pwd.value);   // P2 = base64(password)
```

so the request is `POST /cgi-bin/dologin` with `P2=<base64 password>` and the
`gnkey` value the login page hands out (`0b82` on the audited unit). The session
is a `session_id` cookie. Note the password field is the *only* field: this model
does not ask for a username on the login form.

### It is a two-step exchange, not a single POST

The first form posts `P2` with `gnkey`. If the password is not accepted, the
answer is **not** a plain rejection: it is another form,

```html
<form action="dologin" method="post" name="loginErrForm">
  <input name="session_token" type=hidden value="e9e84da80cb6942ebe929178c8306ffd">
  … Sorry, your login password is not recognized, or you do not have access
  privilege. Please try again. Remaining Attempts: 3
```

so the password is posted a second time with `session_token` in place of
`gnkey`. Only then does the box either set `session_id` or count a refusal.
The counter is in the page text (`Remaining Attempts: N`), which is how the
client knows to stop before it reaches zero.

### The lockout, which is the dangerous part

Five refused passwords lock the console for **fifteen minutes**, and the counter
is readable **without a session**:

```
GET /cgi-bin/api-get_lockouts
{"results":[{"locked":"true","remain":"885","accessattempt":"5","invalidattempt":"10"}]}
```

The timer restarts on the next refused attempt. This is why the client reads the
counter first and refuses to send a password while the box is counting: a retry
loop against this device does not recover it, it extends the outage. During this
audit, ten attempts (mostly malformed on purpose, while establishing the format)
cost 25 minutes of console access.

### Confirmed without a session

| Endpoint | Answer |
|---|---|
| `/cgi-bin/api-get_lockouts` | lockout timer and counters |
| `/cgi-bin/api-get_system_status` | `vsz` (voice image), `command` (= `ata`) |
| `/cgi-bin/api-get_sip` | `{"exist":"false"}` |

Everything else under `/cgi-bin/` needs the session cookie.

### Credential status on the audited unit

**The login was not obtained.** Two POSTs were made — `P2+gnkey`, then
`P2+session_token` — and both returned *"your login password is not recognized"*,
leaving `Remaining Attempts: 2`. At that point the audit stopped on purpose:
two more refusals cost fifteen minutes of console, and the most likely cause is
the credential itself rather than the encoding (the encoding is the page's own
`btoa`, and the two-step shape was reproduced exactly). Everything below the
login — the FXS port table, the account page's field names, the P-numbers the
firmware actually writes — is therefore **unverified on this unit**.

What that means in practice: the client and console are complete and work against
the unauthenticated surface (reachability, lockout, voice image, SIP presence),
and the authenticated path is written to the observed protocol but has never seen
a successful session. Confirm the admin password before relying on the port and
account panels.

## What the console does about it

`src/lib/ata/raw.js` is a raw-socket HTTP client, because no HTTP library will
parse these responses: it normalizes both line endings, keeps the *last* status
line, records non-header junk (the shebang) instead of discarding it, and decodes
as `latin1` so firmware strings survive.

`src/lib/ata/ht802.js` is the device: base64 login, `session_id` cookie, and an
`overview()` that never throws for a reason the page can explain. It reports one
of four states — `online`, `locked`, `auth`, `unreachable` — and only signs in when
the box is not locked.

`src/routes/ata.js` exposes that as JSON behind the platform's own auth, so the
password stays server-side and no device page is proxied to a browser.

`web/src/pages/Device.jsx` is the new console: connection state with a live
lockout countdown, the two FXS ports, the SIP account per port, the network
summary, and where the unit fetches its configuration.

## Voice path: Cantus

The deployment's voice protocol is [Cantus 1.0](https://github.com/innotelinc/cantus):
one UDP socket (7443), 14 message types, its own capability negotiation, and a
relay that makes NAT traversal a property of the protocol rather than six knobs.
It is not SIP, and it does not carry SDP or RTP.

That has one consequence the adaptor cannot avoid: **the HT802 is a SIP endpoint**.
Its web UI configures a SIP server, a SIP user ID and a SIP auth password, and
none of its firmware knows what a Cantus `REGISTER` is. So a unit on a Cantus
deployment registers over SIP to a **SIP↔Cantus edge**, and the edge carries the
call over Cantus from there. That edge is the one piece this repository does not
contain — it is neither in Telno nor in Cantus today. The console says so rather
than implying the box speaks Cantus:

- `CANTUS_SIP_EDGE` (host:port) is written into the adaptor's config as its SIP
  server (P47). With it set, the voice path reads `SIP → edge → Cantus 7443/udp`.
- With Cantus enabled but no edge set, the console says the adaptor falls back to
  the platform's own SIP domain — which is what actually happens.
- With `CANTUS_ENABLED=false` the page shows a plain SIP path and says nothing
  about Cantus.

A second consequence, stated in Cantus's own Appendix D: **T.38 is out of scope by
design**. An HT802 is often bought to put a fax machine on the network, so a
fax behind one of these needs its own SIP path — provisioning over Cantus will
not carry it.

## Honest limits of this audit

- The **authenticated** pages were never reached (see above): the password was
  refused with two attempts left, so the exact page names and field labels on
  this firmware are **not yet verified**. Field extraction is written to be
  layout-tolerant (label → value across table rows and inline `<b>` labels) and
  reports "not reported" rather than inventing a value.
  `GET /api/ata/pages/<id>` exists for that verification pass once the password
  is confirmed.
- Port 2 of the unit was not separately observed; the provisioning template
  turns it off rather than guessing a second account onto the same MAC.
- `POST /cgi-bin/reboot` is implemented from the firmware's convention, not
  observed on this unit (a reboot would have cost another console outage mid-audit).
- The P-number mapping for the adaptor branch (P271/P35/P3/P47/P40 for port 1,
  P401/P735/P703/P747/P740 for port 2) comes from the HT802 documentation, not
  from a config read off this unit. It is deliberately separate from the GXP
  handset mapping in the same file, because writing handset numbers into an
  adaptor produces a file that applies and leaves both ports dead.
- **Superseded by measurement.** On the unit at `192.168.1.5` (`DP750`) that
  mapping is inert: `P35`/`P735` are written, acknowledged and ignored, and the
  values that actually register are the `P4060`/`P4090`/`P4120`/`P4180` block
  documented below. The compat file keeps the documented HT8xx map because that
  is what a genuine HT8xx reads; it is not what this base uses.

## Operating it

```bash
# What the console shows, from a shell
ATA_HOST=192.168.1.45 ATA_PASSWORD=… npm run ata:check
ATA_HOST=192.168.1.45 ATA_PASSWORD=… npm run ata:check -- --json
```

Deployment: set `ATA_HOST` (the unit's LAN address), `ATA_PASSWORD`, and
optionally `ATA_USER` / `ATA_PORT` / `ATA_TIMEOUT_MS` / `ATA_CACHE_SECONDS`.
Leave `ATA_HOST` empty to leave the console page dark. On a Cantus deployment,
set `CANTUS_ENABLED=true` and `CANTUS_SIP_EDGE` so adaptor configs point at the
edge instead of the platform's SIP domain.

To bring a unit up as a Telno device: add it in **Estate** as kind `ata` with its
MAC, then point the unit's *Config Server Path* at the platform's provisioning
URL. It fetches its extension, display name and check-in token on reboot.

# The second unit: firmware 1.0.21.33 (V2)

Measured at `192.168.1.5`. Same product family, **different protocol in every
respect** — so the client detects rather than assumes.

| | V1 (`192.168.1.45`) | V2 (`192.168.1.5`) |
|---|---|---|
| Web server | mini_httpd 1.30, plain HTTP | lighttpd 1.4.55, **TLS only** (`301 → https://`) |
| Console | server-rendered CGI + jQuery | GWT single-page app |
| Login body | `P2=<base64 password>` + `gnkey` | **`username` + `password`, plain** |
| Session | `session_id` cookie | `sid` + `session-identity`/`session-role` cookies |
| Reads | `api-get_*` (3 endpoints) | `POST /cgi-bin/api.values.get`, colon-separated P-numbers |
| `curl` works | no | yes |

## The login, from the shipped client code

The GWT bundle (`/webapp/<permutation>.cache.js`) builds the request directly:

```js
username=<user>&password=<pw>          // password trimmed, NOT base64
// password = hash(password + token) only when a :token field is present
```

`P2=` — correct for V1 — is answered `{ "response": "error", "body": "wrong4" }`
on V2. The trailing digit is the attempts left.

## The stale-session trap

A read is `request=P68:P271:…&sid=<sid>`. Without the `sid`, or with a session
the unit has quietly dropped, the answer is still:

```json
{ "response": "success", "body": { "P68": "", "P271": "", … } }
```

**Empty does not mean "nothing configured".** It usually means "ask again". This
was observed directly: a read returned `P47 = 192.168.1.30`, and a later read with
the same session returned `P47 = ""` while `P40 = 5060` still answered. The client
therefore treats a blank firmware string or serial number as a stale session,
re-authenticates once, and re-reads — and only then reports that it could not read.

## What this unit actually is

`phone_model` answers **`DP750`** (vendor `Grandstream`, `P68 = 1.0.21.33`,
`serial_number = 207GHTXLB0390706`). It is a DECT base with **ten SIP account
slots and no FXS ports at all**. Earlier notes in this file described "FXS 1" and
"FXS 2" through `P271`/`P401`/`P35`/`P735`; those numbers were guesses, they are
unrelated parameters, and writing them changed nothing. The console now reports
the model the unit gives it and calls the lines lines.

## The account map, from the console's own pages

The shipped webapp loads its page definitions from `json/contents/<page>.js`. The
account table is `dect_acct_settings`, and its columns are `SIP_USER`, `SIP_AUTH`,
`SIP_PASS`, `SIP_NAME`, `SIP_PROFILE`. Each cell resolves to one of two keys, and
only one of them is writable:

| Meaning | Writable key (account *n*) | Live value on this unit |
|---|---|---|
| SIP user id | `P4060 + (n-1)` | `201` / `202` |
| Authenticate id | `P4090 + (n-1)` | `201` / `202` |
| Authenticate password | `P4120 + (n-1)` | set (reads back in clear text) |
| Display name | `P4180 + (n-1)` | `Fire panel line` / `Lift line` |
| Registration state | `P4921 + (n-1)` | `1` = registered, `2` = not registered |

The dotted form — `account.1.sip.user_id`, `account.1.sip.subscriber.password`,
and so on — reads back correctly and **is a projection**. `POST api.values.post`
accepts it and answers `{"status":"right"}` while changing nothing. That is the
whole reason this product spent hours writing identities the unit ignored: the
read was real, the write was a no-op.

`P4921`/`P4922` also prove this firmware *does* report live registration, unlike
the V1 units. With `P4060=201, P4090=201, P4120=<extension secret>, P4180=Fire
panel line` and the same for account 2, both accounts came back `1` within
seconds of the write, with no reboot and no provisioning cycle:

```
before   P4060 774505••••  P4061 857990••••  P4921 1  P4922 2
write    P4060 201       P4061 202       P4090/4091 201/202  P4180/4181 names
readback P4060 201       P4061 202       P4921 1  P4922 1
```

The number on account 2 was never a hidden flash value or a stale provisioning
artefact: it was simply **account 2's user id**, sitting in `P4061` the whole
time, next to a live account 1 that belongs to a real customer. (Both are masked
here; they are customer numbers, not fixtures.) Clearing account 2 meant writing
account 2, which the API can now do.

## Setting or clearing a line by API

`POST /ata/accounts` (operator role) writes the block above and then **reads it
back**, because the device acknowledges a write before applying it:

```json
{ "account": 2, "extension": "202", "secret": "…", "name": "Lift line" }
```

Answers `applied: true` only when `P4060+n` and `P4090+n` return the new values.
A refusal or a silent drop comes back as `applied: false` with the reason, never as
success. The password is written but never read back, returned or logged.

## Writing values (verified)

There is a write endpoint, and its shape is only visible in the shipped client
(`webapp/AC4BE19E3DCDE78FA1CF3A5F20E9C377.cache.js`, function that builds the
body):

```
POST /cgi-bin/api.values.post
content-type: application/x-www-form-urlencoded

P35=201&P3=<secret>&P735=202&P703=<secret>&sid=<sid>
```

- Keys are bare parameter names joined by `&`; the client prefixes `P` only when
  the name does not already start with it.
- **`sid` is appended as a final field** (`'&sid=' + sid`), not sent as a cookie.
  A cookie alone is not enough.
- The answer is `{"response":"success","body":{"status":"right"}}` — `right`,
  not `ok`. A refused or stale session answers `error` instead.
- Values persist immediately: a read-back straight after the write returns them.
  No separate save or apply step was needed on `1.0.21.33`.

Writes made on this unit (baseline captured first, so they can be restored):

| Parameter | Before | After |
|---|---|---|
| `P35` / `P3` (claimed "FXS 1") | empty / empty | acknowledged, **value never stored** |
| `P735` / `P703` (claimed "FXS 2") | empty / empty | acknowledged, **value never stored** |

The first attempt used those numbers. `api.values.post` answered
`{"status":"right"}` and the read-back was empty every time, because the unit has
no FXS ports and those parameters are not the account. The block that does work —
`P4060+n` user, `P4090+n` auth id, `P4120+n` password, `P4180+n` name, `P4921+n`
state — is in **The account map** above, and is what `POST /ata/accounts` writes.

**A user id and secret are not a registration.** After the write, a REGISTER to
`192.168.1.30` with the same credentials was answered `401 Unauthorized` both
before and after digest authentication — at that moment the switch did not know
those accounts. 201 and 202 were then created on the PBX itself (FreePBX 17 in
the `zeus-freepbx` container on `192.168.1.30`), and the same credentials now
register `200 OK`:

```
201 -> 200 OK
202 -> 200 OK
```

This firmware does report live registration after all — per account, in
`P4921+n` — so the console says `registered` when the unit says so, and
`not registered` otherwise. It does not infer either.

# Profiles replace provisioning templates

The per-manufacturer templates are gone. The platform speaks one protocol —
Cantus — so it issues one profile, in its own format:

- **`telno`** (`application/json`) — `telno-device/1`: device identity, the line,
  a `voice` block (protocol, endpoint `cantus://host:7443`, realm, capabilities,
  `traversal: reach`), an optional `sip` block for a SIP↔Cantus edge, and the
  check-in token.
- **`terminal`** (`application/xml`) — the same facts as `<telno-profile>`, for
  the box on the wall. No vendor schema, no vendor element names.

Served by MAC at `/provision/telno/<mac>.json` and `/provision/terminal/<mac>.xml`,
ring-fenced exactly as before: an unknown MAC is a 404, and fetching a profile
rotates the check-in token.

Not implemented, and said so in the console: **reboot on V2**. Its restart lives
behind a numeric console operation (`api-sys_operation`) that has not been
verified, so the console refuses rather than guessing.

## The compatibility serializer (`compat`)

`telno` and `terminal` describe the platform. A stock adaptor parses neither: it
wants its own configuration format and will not accept anything else. So there is
a third kind, and only a third kind, that emits that format:

| Kind | Media | For |
|---|---|---|
| `telno` | `application/json` | Telno endpoints and the edge — **the profile** |
| `terminal` | `application/xml` | `<telno-profile>`, the same facts for a wall box |
| `compat` | `application/xml` | **opt-in only**, a unit that must fetch a file it can parse itself |

Served at `/provision/compat/<mac>.xml`. It is never the default: `/api/ata/provisioning`
reports `terminal` unless `?format=compat` is asked for, and Estate exposes it as a
third choice in the dropdown.

What it writes, and nothing else — the documented HT8xx configuration keys:

```
P271  port 1 active        P401  port 2 active (left 0)
P35   port 1 SIP user      P735  port 2 SIP user
P3    port 1 auth password P703  port 2 auth password
P47   port 1 SIP server    P747  port 2 SIP server
P40   port 1 local port    P740  port 2 local port
P140/P141/P142  check-in endpoint, token, interval
```

Those keys are the HT8xx layout. They are **not** what the DP750 at
`192.168.1.5` reads for its accounts — it ignores them — so a compat file should
only be sent to a genuine HT8xx. For the base, use `POST /ata/accounts`.

The `P47` written is the SIP↔Cantus edge when `CANTUS_SIP_EDGE` is set, so a
compat-provisioned unit still lands on Cantus — it just speaks SIP for the first
hop because that is all it has.

**Not verified:** that this unit ingests the file. Pointing its config server at
the platform is a change to the device's own configuration, so the serializer is
written against parameters read from the device and left for an operator to try.
If it is refused, the telno profile plus an edge is the path that is known to work.
